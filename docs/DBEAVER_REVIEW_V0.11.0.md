# V0.11.0 整体检查与 DBeaver 对照建议

检查日期：2026-10-14。基线：`88cb0bbb4fd9030acf7a6035d586f4221db760c0`，V0.11.0 / 构建 17。

本次交付是代码审查、验证证据和后续建议，没有修改应用行为、提升版本号或发布新 APK。以用户提供的 DBeaver 操作界面和常见维护流程为参照，不宣称逐项复现某个 DBeaver 版本或商业版能力。

## 结论

当前已经具备直连、数据库与对象浏览、表收藏、分页表格、列筛选排序、SQL 补全和 AI 当前表操作的基础。但“打开表 → 快速定位 → 连续修改 → 确认结果”仍不够连贯。下一阶段应优先解决状态丢失、编辑效率和正式发行门禁，再扩大引擎数量。

十种连接类型不等于十种引擎都支持增删改查：图形化写入和 AI 写入目前只开放 SQL Server，且限符合条件的单条记录。MySQL、MariaDB、PostgreSQL、SQLite 以及文档、键值、搜索引擎当前仍只读。

## 已确认的问题与体验缺口

“代码确认”表示相关路径明确存在，不表示本轮已在手机上复现；“离线复现”使用真实编译后的核心类、合成元数据，不连接业务数据库。

| 优先级 | 发现与影响 | 证据 | 建议与验收标准 |
|---|---|---|---|
| P0：正式发行前 | Release/R8 尚未通过。上版记录 193 个缺失类，交付仍为 Debug；移除“测试”文字不等于完成正式版验收 | 历史 `docs/evidence/v0110/summary.json`、`docs/TEST_REPORT.md`；本轮没有重跑 Release | 按驱动拆分必需/可选依赖和 Android 适配；Release 实际安装并执行 TLS、查询、写入、升级；不能整体压制缺失类警告 |
| P1：状态处理 | 普通操作失败也清空结果。查询输入错误、预览校验失败等非断连错误都会令表格消失，随后当前表上下文也丢失 | 代码确认：`WorkspaceViewModel.kt:471–476` 的 `failure()` 无条件清空 `result`；`execute()` 共用此路径 | 区分输入错误、读失败、写入冲突和结果未知。非致命失败保留上次结果并标记旧数据，禁止复用失效写入预览；测试错误 SQL、非法编辑、网络中断三条路径 |

| P1：数据类型 | 合法 MySQL/MariaDB `BIGINT UNSIGNED` 超过有符号 Long 范围时，能精确显示却不能按值筛选 | 离线复现：`TableView.kt:41` 的 `toLong()` 拒绝 `18446744073709551615`；读取层 `JdbcResultReader.kt:19` 已单独处理无符号值 | 在元数据中保留有符号范围，使用精确整数/Decimal 绑定；服务端验证最大值、边界附近值和越界值，不转 Double |

| P1：全屏维护 | 全屏只有网格，分页/刷新/新增/删除工具栏留在外层，操作时需要退出全屏；双击编辑也会退出 | 代码确认：`ResultGrid.kt:189–200` 对照 `WorkspaceScreen.kt:204–217` | 共享常驻底栏和编辑入口，全屏支持翻页、新增、删除及变更预览；窄屏横向收纳次要动作，保留可见主操作 |
| P2：SQL 上下文 | 字段补全直接依赖当前结果的 `tableSchema`；执行自写查询后结果不带表结构，原有字段候选随之消失 | 代码确认：`SqlEditor.kt` 的 `suggestions` 参数、`WorkspaceViewModel.kt:396`、会话 `select()` 返回查询结果 | 将选中对象的元数据与结果集分开；再补 FROM/JOIN 别名解析。验证“开表→执行 SQL→继续输入 WHERE”仍有正确字段提示 |

上述状态处理问题不能直接证明用户先前每次“看不到数据库”都由同一原因造成；它们是本次基线中明确存在的潜在触发路径。

## 按日常使用收益排序的新增功能

| 阶段 | 功能 | 对移动端的具体价值与完成标准 |
|---|---|---|
| 下一轮：维护效率 | 表格操作整合 | 选中单元格后提供“按此值筛选 / 排除此值 / 复制 / 设为 NULL / 编辑”；直接看见选中行和待修改数量；没有权限或定位键时说明原因 |
| 下一轮：维护效率 | 筛选与排序编辑器 | 条件回填、多个排序字段的优先级、日期/数字输入器、筛选收藏；随后支持 OR 分组和 IN。所有值保持参数绑定，筛选在数据库端执行 |
| 下一轮：维护效率 | 表视图状态 | 按连接+库+Schema+表保存列宽、隐藏列、排序和筛选；手机抽屉对象导航、平板常驻对象栏。先解决切表返回后上下文丢失 |
| 第二轮：编辑器 | 多表与 SQL 标签 | 每个标签独立草稿、结果和视图状态；关闭未保存草稿有提示，限制缓存。多个标签可以共享串行会话，不必一开始为每个标签开连接 |
| 第二轮：编辑器 | 查询历史与 SQL 工具 | 最近查询、执行时间、行数、连接上下文；查找替换、格式化、行号、语法高亮、执行选中语句。历史设条数和保留期，可关闭/清除，不记录密码或结果数据 |
| 第二轮：编辑效率 | 暂存修改与统一提交 | 多单元格修改先留在本地，高亮差异，提交前一次预览；“撤销”只撤销未提交草稿。应用重启不自动提交；服务端提交使用短事务及原值冲突检测 |
| 第三轮：能力覆盖 | MySQL/MariaDB/PostgreSQL 安全 CRUD | 分引擎补定位键、类型绑定、并发检查、事务和未知结果处理，各自通过 Android 实连后开放；不能只移除只读开关 |
| 第三轮：数据交换 | 受控整表/筛选结果导出、CSV 导入预览 | 分批流式导出、取消、编码/NULL/精度保真；导入先映射字段和预览错误，再显式提交。导出仍不称完整数据库备份 |
| 后续：结构工具 | 索引、约束、外键、DDL 查看、执行计划 | 先补只读结构诊断和跨对象搜索，再做 DDL 设计器；明确各方言不同，不直接让模型执行任意 DDL |
| 后续：连接与设置 | SSH 隧道、配置迁移、超时/页大小设置 | 按真实访问场景实现；配置导出默认排除密码，导入预览并保留原配置；页大小和超时有上限，不取消内存/响应预算 |

建议先做“状态保留 + 筛选回填 + 全屏常用操作 + 数值边界”这一组最小闭环，同时单独推进 Release 驱动适配。不要把所有新增项挤进同一次发行。

## AI 助手应补什么

目前已具备三种文本协议、上游模型获取、发送内容预览、当前表受限查询和 SQL Server 单条变更预览。它不是能自主维护整个数据库的通用代理。

1. **先改善可理解性**：一句话后显示“目标表、条件、预计动作”；零匹配、多匹配或字段不明时提出具体澄清，保留用户原请求。模型错误与数据库错误分别显示。
2. **增加可控结果解释**：由用户选择少量结果行并预览脱敏后，才允许发送给模型解释；当前不自动发送行数据的行为应保留。
3. **写权限范围更清楚**：`AiTableActions.prepare()` 会调用 `setWritable(true)`，生成预览后会话保持可写。当前实际提交仍需确认，但页面只强调“允许当前表生成写入预览”。建议区分单次 AI 写入授权与手工编辑模式，或明确显示会话变化及退出入口。
4. **补整条链路测试**：把模型返回计划、AI 预览、人工确认、真实 SQL Server 写入和结果刷新放在同一个 Android 用例中；再测用户取消、切库、错误目标、冲突、超时及旧响应。目前已有分层用例，不等于完整链路全部实测。
5. **统计/多表最后扩展**：先增加受限聚合与只读跨表计划，再评估批量操作；保留目标绑定、字段验证、影响范围预览，不能把任意模型 SQL 当作可靠指令。
